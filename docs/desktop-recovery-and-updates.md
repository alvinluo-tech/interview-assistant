# 浮窗、副屏恢复与客户端更新设计

日期：2026-10-29。本文区分本次已修复内容、后续更新器设计与尚待验证的风险，不将浏览器模拟等同于真实手机或 Mac 验收。

## 本次问题与修复

| 问题 | 原因与处理 | 验证 |
| --- | --- | --- |
| 底色浓度滑杆、双机位预设看不出效果 | 入口没有给 html/body 设置 overlay 场景标记，透明壳层下面仍是主题的全不透明背景；入口在渲染前设置两个标记 | 原始入口浏览器测试先测得白色 body，修复后 html/body/root 均透明 |
| 手机连接后电脑内容仍可见，却无法操作 | 同一组缺失标记使接管隐藏 CSS 无法匹配；同时本地热区已被接管 | 浏览器验证接管时 root opacity 为 0，恢复时为 1 |
| 切回电脑后按钮仍无法触发 | 原生热区已清空，但本地扫描器认为坐标未变而跳过重新发布 | 副屏退出通知扫描器重建热区；会话、迟到注册与异步清理有代次保护 |
| 组件卸载后迟到的事件监听仍保留 | 通用事件桥只清理已经返回的取消函数 | 注册完成时检查是否已卸载，立即取消迟到监听，屏蔽迟到回调 |
| 透明模式的按钮仍有明显底色 | chip 背景计算没有乘随整体底色下降的系数 | 零底色与 3% 底色分别验证笔试、面试的嵌套控件 |
| 手机缺少明确的结束入口 | 原页面只有切回电脑，不能结束笔试 | 增加单独的结束按钮与确认；断线、等待状态禁用业务动作 |
| 手机追问点击无效 | 页面发送中文 label，宿主识别固定 intent | 使用固定动作编号，显示文字单独保留 |
| 退出后旧连接还能存活 | 服务端读循环未检查当前连接所有权；清除 sender 不会使仍持有自身 sender 的读循环自动结束 | 每次轮询及转发前检查会话代次与连接身份，停止或替换后关闭 socket |
| 令牌校验不精确 | 原逻辑只检查 URL 是否包含令牌，停止服务时空令牌还会匹配任意路径 | 改为固定路由、GET、非空且唯一的完整 token 参数匹配；令牌使用 OS 随机源 |
| 异常连接长期不释放或内存积压 | 缺少主动存活检查、消息与发送队列边界 | 限制帧/消息 64 KiB、队列 8 项、写超时 2 秒；5 秒探活、20 秒无有效回应关闭 |
| 结束后答案迟到或重复解题竞争 | 请求没有取消与代次检查 | 结束、重置取消请求；会话创建、截图和流式完成均检查代次；串行作答 |
| 追问答案重复 | 已逐字追加，又在完成时追加完整答案 | 完成时用完整结果替换流式部分 |
| 保存失败导致退不出去 | 保存与窗口清理串在同一成功路径 | 清理放入 finally，仍保留错误；正常退出先保存已生成的部分答案 |
| 显示版本长期为 0.1.0 | 前端常量没有跟随 tag 准备步骤更新 | 改为读取 package.json；更新检查默认使用官方仓库，拒绝未支持的系统 |

“双机位”仅降低软件绘制的底色浓度，默认保留文字可读性；不保证外部摄像头看不到文字。手机副屏则将本地内容完全隐藏，两者用途不同。

## 副屏操作与恢复约定

1. 电脑生成二维码，手机显示“已连接，等待电脑开始笔试”。拿到宿主状态前不能解题。
2. 笔试浮窗已启动时，手机接管内容；电脑保留透明的鼠标映射区域。手机可以直接点按操作，不必依赖电脑鼠标。
3. **切回电脑**：恢复原来的电脑尺寸和热区，保留当前作答内容，关闭本次副屏服务与旧令牌。手机清空答案，不再自动重连；再次使用需在电脑生成新二维码。
4. **结束本次笔试**：手机先确认，宿主取消生成、保存当前部分答案、完成记录、关闭浮窗并回到工作台，同时停止副屏。
5. **短暂断线**：保留 15 秒重连宽限；超时恢复电脑。主动停止、更换二维码不走断线宽限，立即恢复。
6. **浮窗被隐藏或退出**：主动释放手机连接，避免手机一直显示“已连接”却没有可响应的宿主。
7. **恢复入口**：手机始终保留切回入口；电脑工作台保留“切回电脑并停止副屏”；原有应急快捷键继续可用。不能只依赖一个可能断线的控制端。

## 自动更新的交互

推荐采用自动发现、用户确认安装，初期不做强制升级。

- 主窗口启动完成后延迟检查，不阻塞启动；同一版本每天最多主动提示一次。设置页始终可手动检查。
- 空闲状态发现更新，弹窗显示：当前版本、新版本、发布时间、更新说明、是否需要重启。按钮为“稍后提醒”“下载更新”，附“查看完整发布说明”。
- 面试、笔试、录音或副屏接管中，只在主窗口显示“有新版本”标记；不在浮窗、手机页或正在共享的画面弹更新窗口。
- 点击下载后显示下载大小、已下载量和进度。下载失败可重试、可前往官方发布页；检查失败与“已是最新版”必须区分。
- 下载完成显示“更新已就绪”，按钮为“稍后安装”“重启并安装”。会话进行中禁用安装，并说明须先结束当前会话。
- 安装前重新检查活动会话，停止采集和副屏，完成记录、刷新设置到磁盘，再正常退出。不能只相信页面刚打开时的空闲状态。
- 下次启动确认实际版本已经变化，再显示更新成功；失败时保留旧程序和手动下载入口。初期不承诺断点续传、无感后台安装或自动降级。

建议原生维护状态：idle → checking → available → downloading → ready → installing；任何阶段都可进入 error，重试应有明确入口。检查、下载、安装各自单例；多个窗口不能同时启动安装任务。

## 更新器与 GitHub Release 的衔接

采用 Tauri v2 官方 updater。启用更新产物并配置固定 HTTPS 更新地址及公钥。Windows 使用 NSIS 安装文件及签名；Mac 使用 `.app.tar.gz` 及签名，DMG 继续供手动安装。GitHub Release 增加 `latest.json`，平台键分别是 `windows-x86_64`、`darwin-aarch64`、`darwin-x86_64`，每项提供对应下载 URL 与签名。签名不可关闭，SHA-256 校验和不能替代签名。[官方 updater 文档](https://v2.tauri.app/plugin/updater/)

具体改动分为四层：

| 层 | 实施位置与要求 |
| --- | --- |
| 原生更新服务 | 新模块统一检查、下载、校验、安装；更新权限仅给 main；在安装前原生再次检查 session_active 与采集状态 |
| 前端界面 | 主窗口更新状态提示、更新弹窗、设置页进度与重试；复用同一服务，避免两个入口状态不同步 |
| 版本与存储 | 真实版本来自发布准备后的清单及原生版本；保存稍后提醒、跳过版本、更新任务结果，不能缓存 API Key 到更新元数据 |
| 发布与 CI | 三平台各自生成并验证签名产物；全部成功后统一组装 latest.json，并在 Release 草稿中上传齐全再公开 |

更新地址建议固定为官方仓库的 `releases/latest/download/latest.json`。普通手动下载仓库设置与受签名保护的自动安装源分开，不允许通过输入任意仓库绕过更新公钥。

私钥只在首次接入时生成并单独备份，在正式发布的构建任务中通过 GitHub Actions secrets 注入 `TAURI_SIGNING_PRIVATE_KEY` 与 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`；源码只放公钥。普通 PR/main 验证禁用更新签名产物生成，不接触生产签名密钥。正式 tag 发布缺少签名或任一架构失败必须停止公开发布。此次只完成设计，没有生成生产密钥或修改 GitHub secrets。

## 安装方式的边界

- **Windows 安装版**：正常路径可通过 NSIS 更新；安装器会使应用退出，需先协调会话与守护进程的正常退出。以 [官方 Windows 安装钩子](https://v2.tauri.app/plugin/updater/#windows-before-exit-hook) 为接入点之一，不能等进程退出后才保存记录。
- **Windows 免安装 EXE**：首期保留手动下载，避免安装器突然改变原来的使用方式。识别安装版时应核验卸载信息与规范化安装路径，不能仅靠文件名猜测。
- **Windows 伪装副本**：先恢复并重启原安装位置的主程序，再重新校验待安装更新。不能对缓存中的改名副本直接执行覆盖更新。
- **Mac**：区分 DMG 挂载位置、Applications 安装位置、目录写权限。更新签名和 Apple Developer ID/公证是两套机制；前者不代替后者。
- **已有 v0.1.1 用户**：旧版未集成 updater，不能凭服务端多传一个文件就获得自动安装能力。需要手动安装首个带 updater 的版本，之后才能走上述流程。

## 自检后仍待处理或验收

| 优先级 | 项目 | 当前判断 |
| --- | --- | --- |
| P1 | 笔试会话跨 WebView 的所有权 | 代码审查发现工作台提前创建会话，而浮窗维护独立内存状态并可能再次创建；还需双 WebView 端到端复现。建议会话统一由浮窗掌管，主窗口只传启动配置，避免空记录及岗位关联丢失 |
| P1 | “直接答”动作 | 当前 answerNow 仍是占位实现，不能宣称能让模型立即给出最终答案；需明确产品语义后实现或取消入口 |
| P1 | 真正的下载、验签与安装 | 当前仍为手动检查并打开下载链接；上述 updater 尚未接入，不将设计当成已实现 |
| P2 | 手机网络服务承载 | 仍是本地 HTTP/WS，限可信局域网，不面向互联网暴露；后续可迁移成熟 HTTP 服务栈并补连接总数限制与 Origin 策略 |
| P2 | 手机与 Mac 实机 | Safari/微信内置浏览器后台挂起、缩放/横屏、锁屏、Wi-Fi 切换、Windows 不同 DPI、Mac 多屏仍需实际设备验收 |

现有 HTTP/WS 中断探测还受浏览器与操作系统调度影响；15 秒是确认断线后的恢复宽限，不代表物理断网后必然 15 秒内恢复。

## 验证方式

```sh
pnpm test:platform
pnpm test:core-coverage
pnpm test:release
pnpm build
cargo test --locked --manifest-path src-tauri/Cargo.toml --workspace --lib
```

浏览器检查真实浮窗入口和原生内嵌手机页，不读写应用的个人配置：在独立终端设置 `MIANSHI_UI_SMOKE=1`，启动 `node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 1438 --strictPort`，再执行 `node scripts/overlay-ui-smoke.mjs`。浏览器可通过 `UI_TEST_BROWSER` 指定；手机页使用合成 WebSocket，不向局域网或 AI 服务发送请求。

自动更新上线前另需做完整升级演练：有效/篡改签名、架构不匹配、下载失败、磁盘不足、会话中禁止安装、伪装进程恢复、更新失败后旧版可用，以及至少一次 Windows 与 Mac 的旧版到新版安装。

本次本地验证：完整 JavaScript 回归通过（新增通用事件测试后共 123 项）；Rust 工作区 43 项通过、1 项音频硬件测试跳过；前端构建及浏览器检查通过。既有四模块核心覆盖率为行 98.15%、分支 84.44%、函数 85.94%，这些数字不代表整个桌面应用或新增副屏模块的覆盖率。
