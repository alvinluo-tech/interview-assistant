# 实时面试语音发送积压复核

日期：2026-11-06。

## 结论

“语音发送积压超过两秒，请检查网络后重试。”存在可复现的发送端诱因，不能仅凭此提示判定公网网络不佳。该提示来自持续实时 ASR 的 PCM 发送队列，和模型生成答案的队列不是同一回事。

16kHz、单声道、PCM16 每秒 32000 字节；原实现用 64000 字节作为两秒积压上限。它表示待发送音频的时长，不是识别服务已经两秒没有返回结果。

## 已复现的问题

1. 每个采集回调单独串行执行桌面 WebSocket 插件的 `send`，没有合并待发小包。麦克风在 48kHz 下每 2048 样本回调约 43ms，发送端必须承担相应的原生调用频率。原生调用、序列化或调度耗时较大时，公网带宽足够也可能积压。
2. 重连后全局 `sending` 仍受旧连接未完成发送的控制，新连接可能等待旧发送完成或超时才开始传输。
3. 队列在发送前扣除字节，正在发送的音频没有计入两秒上限；原提示不是精确的总待发送音频量。

确定性压力测试：每 20ms 输入 320 个样本、每次发送模拟 80ms 完成。旧代码在模拟时间 2680ms 报积压；修改后连续输入 12 秒正常，384000 字节全部按顺序发送，逐样本验证无丢失、重复或乱序。这是发送端模型测试，不代表实测某台设备的 IPC 延迟是 80ms。

## 修复

- 保留首包立即发送；发送被占用时，将已排队音频合并为不超过 3200 字节（100ms）的帧，减少逐小包原生调用的固定开销，不额外等待定时凑包。
- 发送泵按连接代次隔离，并绑定具体 socket。旧连接的发送完成或失败不能阻塞、清除或消耗新连接的队列。
- 两秒上限同时统计队列和当前发送中的 PCM。单包超过两秒（输入异常）仍停止收音并提示重试；累计积压超过两秒时改为丢弃过期音频、重连实时连接，避免整场面试停止收音。没有通过扩大缓存或静默丢弃音频掩盖问题。
- 保留断线提示、重连间隙不重放旧音频、发送超时和结束前排空队列等边界。

参考：[阿里云 Fun-ASR-Realtime 官方说明](https://www.alibabacloud.com/help/en/model-studio/fun-asr-realtime-python-sdk)建议以约 100ms、1–16KB 的音频帧发送。这里的 3200 字节等于 16kHz PCM16 的 100ms。

## 验证

新增三个回归场景，回放到修改前的版本全部失败，修改后全部通过：

1. 小采集包与 80ms 发送延迟持续并存，检查完整字节顺序和单帧上限。
2. 旧连接的发送仍挂起时，新连接立即发送；旧发送随后完成也不破坏新队列。
3. 完全堵塞时，正在发送的 100ms 加排队的 1900ms 达到边界，再输入音频会停止并释放连接。

实时 ASR、面试音频和语音通话相关的 67 项测试通过；另修复已有原生事件监听测试缺失 `./i18n` 测试依赖的配置问题，该文件 4 项测试通过。

完整回归 337 项全部通过；TypeScript 检查和生产前端构建通过。结果见本机忽略目录 `artifacts/audit/asr-backlog-all-tests.txt`、`asr-backlog-build.txt`；复现对照见 `asr-backlog-baseline.txt`。测试使用模拟发送器，没有录制或上传用户语音，没有使用真实 API Key。

## 使用边界

修复覆盖调用共用实时 ASR 协议的面试、模拟面试和自由语音会话。分段/文件转写使用另一条队列，不由本提示触发。

真实网络长期低于音频产生速率、连接完全阻塞或采集事件一次性补发超过两秒音频时，保护仍可能触发；大模型回答慢本身不能直接解释这条发送队列提示。Windows/macOS 实机上的触发频率仍需连续说话、设备负载及网络抖动测试确认。
